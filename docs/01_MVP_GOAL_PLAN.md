# 구현 목표: 로컬 음성 전사·한글 회의록 MVP

문서 버전: 1.1 | 작성일: 2026-09-27 | 최종 갱신: 2026-09-27 | 선행 조건: `00_PREFLIGHT.md`의 `READY`

> 이 문서는 구현 목표·범위·완료 조건의 기준이다. 마스터가 작업을 쪼개고 구현하며, 검증 세션에는 필요한 범위만 위임한다. 단순 코드 생성이나 mock 테스트 성공만으로 실제 모델·Linux 릴리즈 완료를 선언하지 않는다.

## 0. 마스터 세션의 `/goal` 입력

사전작업을 마치고 두 세션의 연결이 살아 있는 상태에서 **Astra medium 마스터 세션에만** 아래를 입력한다.

```text
/goal AGENTS.md와 docs/01_MVP_GOAL_PLAN.md를 기준으로 로컬 회의록 MVP를 구현하라. docs/00_PREFLIGHT.md의 READY와 실제 환경을 확인한 뒤 G1~G6을 수행하라. 너는 Astra medium 마스터이며 구현·수정·진행 관리를 맡는다. 기존 Sol 5.6 High 검증 세션 하나에만 codex queue로 커밋 고정·범위 제한 검증을 위임하라. 검증은 R1·R2·R3와 필요한 수정 재검증으로 묶고 매 작업마다 전체 검증하지 말라. Codex CLI만 사용하고 Gemini·유료 API 폴백·외부 연동은 구현하지 말라. Windows의 WSL2 개발과 Ubuntu 24.04 CPU 릴리즈를 완성하고, 실제 샘플·취소·복구·릴리즈 증거를 남겨라. 진행·결정·증거는 .workflow에 저장하고 중단 시 마지막 유효 체크포인트에서 재개하라. 모의 시험과 실제 시험을 구분하고 13장의 완료 조건을 충족했을 때만 VERIFIED로 종료하라. 차단되면 독립 작업을 계속한 뒤 원인과 재개 절차를 보고하되 미검증 항목을 통과로 바꾸지 말라.
각 마일스톤 완료 전 12.1절에 따라 실제 결정·구현과 이 문서의 차이를 확인하고 관련 절을 최신화하라. 상세 변경 이력은 만들지 않으며, 미완료 요구를 문서에서 지워 완료로 만들지 말라.
```

공식 `/goal` 지시는 최대 4,000자이므로 목표 문장에는 파일을 참조하고 상세 명세를 반복 붙이지 않는다. `/goal`, `/goal pause`, `/goal resume` 등은 설치된 버전의 도움말로 확인한다. [S1]

검증 세션에는 사전작업 문서의 역할 지시만 입력한다. 검증 세션에 지속 실행 `/goal`을 설정해 할 일 없는 상태에서 반복 검사를 시키지 않는다.

## 1. 제품 목표와 고정 범위

### 1.1 목표

한국어·영어 회의 음성이나 영상을 개인 PC의 웹 UI에 업로드하면, 로컬 CPU에서 전사·화자 구분을 수행하고, **전사 텍스트만 개인 구독 Codex CLI로 보내** 근거를 확인할 수 있는 한글 회의록 초안을 만든다. 사용자는 전사·화자를 고치고 회의록을 수정·확정·내보낼 수 있다.

### 1.2 반드시 구현할 기능

| 기능 | 완료 시 사용자 경험 |
|---|---|
| 업로드 | 음성·영상 파일을 올리고 업로드 진행·오류를 확인한다. |
| 입력 검증 | 최대 2GB·120분, 오디오 존재·형식·트랙을 실제 검사한다. |
| 회의 설정 | 제목, 실제 회의 일시·시간대, 한국어/영어/자동·혼용, 실제 발화자 자동/1~12명을 설정한다. |
| 로컬 전사 | `large-v3-turbo` CPU INT8로 원어 전사문을 생성한다. |
| 시간 정렬 | 한국어·영어 정렬, 실패 구간은 구간 단위 시간으로 대체한다. |
| 화자 구분 | community-1로 전체 회의 기준 화자 ID를 유지한다. |
| 화자 수정 | 이름 변경, 발언 재배정, 화자 병합·실행 취소, 미확정·겹친 발화 표시를 제공한다. |
| 임베딩 보정 | 기존 pyannote 임베딩을 활용한 병합 후보를 제시하되 자동 확정하지 않는다. |
| 한글 회의록 | 요약, 안건, 결정 사항, 담당자·기한 포함 할 일, 미결 사항을 구조화한다. |
| 근거 확인 | 결정·할 일의 참조 구간을 눌러 전사문과 음성 위치로 이동한다. |
| 편집·버전 | 사용자 수정과 자동 원본을 분리하고 새 전사·회의록 버전을 생성한다. |
| 대기열 | FIFO 순서, 현재 단계·경과 시간·대기 순번·차단 이유를 웹에 표시한다. |
| 취소·복구 | 대기 취소, 실행 프로세스 취소, 단계별 재시도, 재시작 복구를 지원한다. |
| 관리·내보내기 | 회의 목록·제목/본문 검색, Markdown·텍스트 내보내기, 삭제·보관 설정을 제공한다. |
| 설치 | Windows+WSL 개발 실행, Ubuntu 24.04 x86_64 설치·진단·실행을 재현할 수 있다. |

입력 확장자의 기본 허용 목록은 WAV·MP3·M4A·FLAC·OGG·MP4·MOV·MKV·WEBM으로 하되 실제 FFmpeg 디코딩 결과로 판단한다. 지원하지 않는 코덱은 명확한 오류로 반환한다. 업로드는 로컬 파일을 대상으로 하며, 이어 올리기 전용 프로토콜은 MVP에서 제외하고 실패 시 재업로드를 제공한다.

### 1.3 구현하지 않을 것

Gemini 및 다른 LLM 공급자, OpenAI API 키 결제, 자동 유료 폴백, Slack·Notion·Confluence 실제 연결, 회의 참여 봇, 실시간 자막, 영상 화면 인식, 음성 분리·음성 복제, 회의 간 실명·동일인 식별, 공개 SaaS·회원가입·조직 관리, 동시 회의 처리, GPU 최적화, RAG·벡터 DB, Kubernetes·Redis·Celery를 구현하지 않는다.

개인용·루프백 전용 범위에 맞춰 조직형 로그인은 제외한다. 대신 **로컬 소유자 접근 제어와 악성 웹 페이지로부터의 요청 차단**은 포함한다. 장비가 다른 사용자의 접근을 허용하는 공용 서비스로 범위를 넓히지 않는다.

## 2. 기술 구조와 디렉터리

### 2.1 실행 구조

```text
Windows 브라우저 / Ubuntu 브라우저
             │ 같은 출처의 웹 요청
             ▼
FastAPI + React 정적 파일
  ├─ SQLite: 회의·영속 대기열·버전·진행 상태
  └─ 로컬 파일: 원본·오디오·모델 결과·회의록
             ▲
             │ 상태 조회·갱신
      단일 작업 관리자
             │ 활성 작업 1개
             ▼
      작업별 별도 프로세스
        파일 검증 → 오디오 추출 → ASR → 정렬
        → 전체 회의 화자 구분 → 발언 연결
        → Codex CLI 한글 회의록 → 결과 확정 저장
```

API 프로세스는 Torch 모델을 로드하지 않는다. 모델 처리와 CLI 호출은 작업 관리자와 분리된 자식 프로세스에서 실행한다. 각 단계 산출물을 저장하고 무거운 모델은 단계가 끝나면 해제한다. UI 요청을 모델 스레드와 같은 이벤트 루프에서 막지 않는다.

## 3. 두 개발 세션과 검증 규약

### 3.1 역할 분담

**마스터: Astra medium**

제품 코드·테스트 코드·설치 스크립트·문서 수정의 유일한 책임자다. 작은 기능 단위로 구현하고 직접 빠른 확인을 한다. 검증 필요 여부, 범위, 실행 예산, 리뷰 요청 시점을 결정한다. 검증 결과를 읽고 수정하며 최종 완료 판정을 내린다.

**검증: Sol 5.6 High**

마스터가 보낸 특정 커밋·계약·위험 지점을 검증한다. 제품 코드나 기준 테스트를 수정하지 않는다. 필요한 재현 코드는 자기 임시 디렉터리 안에 두고 마스터에게 전달한다. 요청하지 않은 전체 저장소 탐색·전체 모델 실행·리팩터링 제안을 반복하지 않는다.

추가 개발 세션·별도 `/review` 세션·재귀 서브에이전트를 만들지 않는다. 제품의 실제 `codex exec` 시험은 도구 실행으로 취급하되 구독 사용량을 소모하므로 별도 예산을 적용한다.

### 3.2 기본 검증은 세 묶음

| 검증 | 시점 | 범위 | 전체 회귀 |
|---|---|---|---|
| R1 | G2 완료 후 | 업로드 보안, FIFO, 상태 전이, 취소·복구 경쟁 조건 | 금지 |
| R2 | G4 완료 후 | 시간축·화자 연결, 원본/편집본 보존, Codex 격리·근거·오류 처리 | 금지 |
| R3 | G6의 릴리즈 후보 고정 후 | 전체 요구 추적, 릴리즈 설치, 전체 자동 회귀, 실제 실행 증거 확인 | 기본 1회 |

G1·G3·G5마다 별도 전체 검증을 추가하지 않는다. 단순 텍스트·스타일·파일명 수정에는 마스터의 관련 테스트만 실행한다. 보안·데이터 무결성·공유 계약 변경은 필요하면 **추가 범위 검증**을 요청할 수 있지만 이유를 기록해야 한다.

여기서 전체 자동 회귀는 정적 검사·단위·계약·mock 기반 E2E 전체를 뜻한다. R3에서도 유효한 실제 모델·CLI·장시간 측정 증거를 무조건 재실행하지 않는다. 모델·설정·영향 코드가 바뀐 경우에만 관련 실제 시험을 갱신한다.

### 3.3 검증 요청 패킷

마스터는 자신의 변경만 커밋하거나 동등한 불변 스냅샷을 만든다. 사용자 작업을 임의로 포함·초기화하지 않는다. 기본은 Git 커밋 SHA이며, 검증용 worktree를 그 SHA로 맞춘 다음 아래 파일을 원자적으로 기록한다.

`.workflow/reviews/<request_id>/request.json`

```json
{
  "request_id": "R1-001",
  "gate": "R1",
  "attempt": 1,
  "base_commit": "검증 기준 커밋",
  "head_commit": "이번 검증 커밋",
  "review_worktree": "절대 경로",
  "scope": ["jobs", "media upload", "cancellation"],
  "changed_paths": ["실제 변경 경로"],
  "acceptance_ids": ["AC-02", "AC-03"],
  "questions": ["취소와 완료가 경합해 결과가 되살아나는가?"],
  "evidence": ["절대 로그/결과 경로"],
  "allowed_commands": ["정확한 대상 테스트 명령"],
  "allow_full_suite": false,
  "allow_model_run": false,
  "allow_live_codex": false,
  "result_path": "절대 경로/result.json",
  "reply_to_thread_id": "마스터 UUID"
}
```

큐에는 긴 원문 대신 ID·SHA·패킷 경로를 보낸다. `codex queue --thread ... --message ...`의 지원 여부는 사전작업에서 확인한 버전을 사용한다. [S2]

```bash
codex queue --thread "$VERIFIER_THREAD_ID" \
  --message "VERIFY_REQUEST id=$REQUEST_ID; commit=$HEAD_SHA; packet=$PACKET_ABS_PATH; 지정 범위만 검증하고 result.json 저장 후 마스터에게 회신하라."
```

검증 세션은 요청 ID·커밋을 확인하고 **동시에 요청 하나만** 처리한다. 큐가 중복 전달되어도 완료된 같은 요청을 재실행하지 않는다. 검증 worktree가 다른 SHA이면 추측해 검사하지 않고 `BLOCKED`를 반환한다.

### 3.4 검증 결과와 회신

검증 결과의 자연어 내용은 한국어로 작성한다.

```json
{
  "request_id": "R1-001",
  "head_commit": "실제로 검증한 커밋",
  "verdict": "PASS",
  "scope_checked": ["실제 확인한 범위"],
  "commands_run": ["실행 명령과 종료 코드"],
  "evidence": ["근거 경로"],
  "findings": [],
  "not_tested": [],
  "requested_expansion": null
}
```

`verdict`는 `PASS`, `CHANGES_REQUIRED`, `BLOCKED` 중 하나다. 문제에는 중요도·파일/행·재현 조건·기대/실제 결과·최소 수정 방향을 포함한다. 추측은 확정 결함과 분리한다.

검증 완료 뒤 결과 파일을 먼저 저장하고 마스터로 한 번 알린다.

```bash
codex queue --thread "$MASTER_THREAD_ID" \
  --message "VERIFY_RESULT id=$REQUEST_ID; commit=$HEAD_SHA; result=$RESULT_ABS_PATH"
```

마스터는 알림 문구가 아니라 결과 파일을 확인한다. 오래된 SHA의 통과 판정을 최신 코드 전체의 통과로 사용하지 않는다. 다만 변경되지 않은 컴포넌트의 증거는 의존 관계·해시가 유효하면 재사용한다.

### 3.5 과잉 검증·유휴 토큰 방지

- 기본은 **변경 범위 검사 → 관련 통합 검사 → 릴리즈 전체 회귀** 순서다.
- 같은 `(변경 지문, 잠금 파일, 설정, fixture, 테스트 명령)`의 성공 증거를 재사용한다. 코드 영향 분석 없이 같은 테스트를 다시 실행하지 않는다.
- R1·R2의 결과에는 기본적으로 실제 모델 추론을 요구하지 않는다. 마스터가 이미 남긴 로그와 고정 입력을 검토하고 의심되는 최소 사례만 재현한다.
- 동일 리뷰의 수정 재검증은 해당 실패와 회귀 위험에 한정한다. 두 차례 재검증에도 해결하지 못하면 마스터가 원인을 정리해 설계나 재현 조건을 바꾼다. 무한 같은 검증 반복이나 미해결 통과 처리는 금지한다.
- 스타일·선호 수준 의견은 자동 차단하지 않는다. 보안, 데이터 손실, 기능 오작동, 필수 완료 조건 미달은 해결하거나 명시적으로 차단 상태로 남긴다.
- 검증 세션이 범위를 넓혀야 하면 이유와 최소 추가 명령을 결과에 적고 마스터가 승인한다. 전체 검증으로 임의 승격하지 않는다.
- 리뷰 대기 중 마스터는 충돌하지 않는 구현을 진행한다. 검증 세션의 snapshot을 바꾸지 않는다.
- 두 세션이 동일 장비에서 실제 ML·장시간 테스트를 동시에 실행하지 않도록 공유 잠금을 사용한다. 해당 잠금은 앱의 FIFO와 별개다.
- 수십 초마다 모델에게 “끝났나?”를 묻지 않는다. `codex queue` 완료 통지를 사용하고, 장시간 외부 명령은 지원되는 프로세스 완료 알림 또는 제한된 로컬 감시 스크립트로 결과를 한 번 전달한다.
- 알림 유실 확인은 로컬 상태 검사로 처리한다. 대상 세션이 닫혔거나 인증이 만료됐다면 보류 상태와 재개 지점을 남기며 제3 세션을 만들지 않는다.

SQLite는 한 장비의 로컬 디스크에 두며 네트워크 공유 드라이브를 지원하지 않는다. 큐 선택·상태 변경은 짧은 트랜잭션으로 처리하고 미디어 처리 중 DB 쓰기 잠금을 유지하지 않는다.

### 4.2 반드시 지킬 불변식

1. 활성 회의 처리 시도는 전체 앱에서 최대 하나다. 프런트엔드 버튼 제한만으로 보장하지 않는다.
2. 시간축은 원본 회의 기준 밀리초다. 모델에 넘긴 청크의 상대 시간을 최종 결과로 저장하지 않는다.
3. 완료 단계 산출물은 파일 원자적 교체와 DB 완료 기록이 맞아야 재사용한다. 파일만 있거나 쓰다 만 결과는 완료가 아니다.
4. 원본 전사·화자 결과는 불변이다. 사용자 수정은 새 버전으로 남기며 확정된 회의록을 자동 덮어쓰지 않는다.
5. 요약은 시작 시점의 전사 버전 snapshot만 사용한다. 생성 중 전사가 바뀌면 새 결과에 “이전 전사 기준” 표시를 한다.
6. 근거 ID는 지정 전사 버전의 실제 구간만 참조한다. LLM이 반환한 시각을 그대로 믿지 않는다.
7. 삭제·취소된 시도의 뒤늦은 결과는 현재 버전을 갱신할 수 없다. 저장 직전 `attempt_id`·취소·삭제를 재확인한다.
8. 편집에는 낙관적 버전 검사를 적용한다. 오래된 편집 요청은 409로 거부하고 내용을 잃지 않게 한다.
9. 사용자 화자 수정은 자동 보정에서 보호한다. 화자 이름·할 일 담당자도 참조 버전에서 해석한다.
10. 재시도·중복 클릭·중복 완료 알림은 새 결과·비용을 무제한 만들지 않는다. 작업 등록에 멱등성 키를 사용한다.

## 5. 업로드·FIFO·취소 명세

### 5.1 업로드와 전처리

HTTP 요청 전체를 메모리에 올리지 않고 스트리밍으로 저장한다. 서버가 실제 받은 바이트를 세어 2,000,000,000바이트에서 제한한다. 사용자가 정한 파일명은 표시용으로만 보존하고 저장 키는 서버가 생성한다. 경로 이동·심볼릭 링크·확장자 위장·중간 끊김·디스크 부족을 처리한다.

업로드 완료와 기본 저장 검증 후 FIFO에 등록한다. 최대 길이·오디오 유무·트랙·코덱은 작업 단계에서 ffprobe로 검사한다. 길이가 불명확하면 제한된 디코딩으로 확인하며 제한 우회를 허용하지 않는다.

오디오 트랙이 하나면 자동 선택한다. 여러 트랙의 대표 선택이 명확하지 않으면 `BLOCKED / AUDIO_TRACK_REQUIRED`로 표시하고 사용자 선택을 받는다. 아무 설명 없이 첫 트랙을 처리하지 않는다.

선택한 트랙만 음성으로 추출한다. 기본 분석 오디오는 16kHz 모노 PCM으로 정규화하되 원본과 트랙 메타데이터를 남긴다. 영상 프레임 분석과 강제 노이즈 제거는 하지 않는다. 미디어 디코더는 로컬 파일만 열게 하고 원격 프로토콜·내부망 접근을 제한한다.

### 5.2 상태와 FIFO

작업 상태와 처리 단계를 분리한다.

```text
state:
  QUEUED → RUNNING → COMPLETED
                    COMPLETED_TRANSCRIPT_ONLY
                    BLOCKED
                    FAILED
  QUEUED/RUNNING/BLOCKED → CANCEL_REQUESTED → CANCELLED
  비정상 종료된 실행 → INTERRUPTED → 명시적 복구

stage:
  VALIDATE → EXTRACT → TRANSCRIBE → ALIGN
  → DIARIZE → ATTRIBUTE → SUMMARIZE → SAVE
```

`BLOCKED`의 이유에는 로그인, 구독 한도, 오디오 트랙 선택, 권한 문제 등을 저장한다. `CANCEL_REQUESTED`는 즉시 완료 상태가 아니다. 프로세스 종료·정리가 확인되어야 `CANCELLED`다. 아직 시작하지 않은 대기 작업은 트랜잭션 안에서 바로 취소할 수 있다.

큐 순서는 업로드 완료/작업 등록 시 부여한 증가 번호다. 재생성 요청도 새 큐 작업이다. 실행 중 재시도는 같은 작업의 새 시도 ID를 만들고 순서를 임의 변경하지 않는다.

head 작업이 인증·한도 때문에 막히면 기본 FIFO는 멈춘다. 사용자는 **재시도 / 전사 결과만 유지하고 종료 / 취소**를 선택한다. 구독 초기화 시각을 실제로 알 수 있을 때만 제한적인 예약 재시도를 제공하고, 알 수 없으면 만들어내지 않는다. 다른 공급자로 자동 전환하거나 다음 회의를 몰래 선처리하지 않는다.

### 5.3 단일 실행과 복구

단일 작업 관리자에 OS 파일 잠금과 DB 원자적 claim을 사용한다. 같은 데이터 디렉터리에 관리자가 두 번 실행되면 두 번째는 진단 후 종료한다. API의 다중 요청이나 워커 재시작으로 활성 작업이 두 개가 되지 않도록 통합 시험한다.

실행 기록에는 PID만 아니라 프로세스 시작 식별 정보, 프로세스 그룹, 시도 ID를 함께 보존한다. 재사용된 PID나 다른 프로젝트 프로세스를 종료하지 않는다. 비정상 종료 후에는 남은 자기 프로세스와 임시 산출물을 확인한 뒤 마지막 정상 단계부터 복구한다.

재시작 복구는 단계 단위다. 모델 내부 진행 상태까지 이어서 실행하지 않는다. `StageArtifact`의 모델·입력·설정 지문이 바뀌면 해당 단계와 이후 단계만 무효화한다.

### 5.4 취소 계약

실행 취소는 취소 플래그 기록 → 정상 종료 신호 → 설정된 유예 후 강제 종료 → 하위 프로세스 종료 확인 → 임시 파일 정리 순서다. FFmpeg, ML 하위 프로세스, Codex CLI까지 포함한다. Linux 프로세스 그룹과 검증 가능한 자식 프로세스 추적을 사용하고, 서비스 실행에서는 systemd의 프로세스 정리 경계도 활용한다.

제품의 기본 목표는 취소 요청이 다음 2초 UI 갱신에 표시되고, 정상 종료 유예 5초 뒤 필요하면 강제 종료되는 것이다. 이는 **구현 목표**이며 실제 확인한 종료 시간과 제한을 기록한다. 강제 종료가 확인되지 않았는데 다음 작업을 시작하지 않는다.

API 서버와 두 개발 세션은 앱 작업 취소로 종료되면 안 된다. 테스트에서는 취소와 완료의 경합, 파일 삭제와 늦은 결과 저장, 중복 취소, 서비스 재시작을 확인한다. 외부 모델 서버에서 이미 처리된 구독 사용량까지 취소된다고 안내하지 않는다.

## 6. 로컬 전사·정렬·화자 구분

### 6.1 CPU 전사

모델은 `large-v3-turbo`, 장치는 CPU, CTranslate2 연산은 INT8로 고정한다. 배치 크기 1, 스레드 4에서 시작하고 실제 장비 측정으로만 조정한다. 세부 모델·리비전·연산 설정을 결과 메타데이터에 저장한다. 모델을 로드하지 않은 mock 경로를 정상 경로처럼 표시하지 않는다. [S3]

한국어·영어 발언을 원래 언어로 보존한다. 영어 전사 전체 번역은 하지 않고 최종 회의록만 한국어로 만든다. 자동 언어 감지는 보조 수단이며 한·영 혼용 품질을 보장한다고 표시하지 않는다.

무음·음악 위주·인식할 수 없는 음성은 경고 또는 분석 불가로 반환한다. 무음 구간에서 생성된 텍스트를 정상 회의 발언으로 무조건 받아들이지 않는다. VAD·전사 경고·대상 구간을 기록해 사용자가 확인할 수 있게 한다.

### 6.2 시간 정렬

한국어와 영어의 검증된 정렬 모델을 사용한다. 혼용 구간은 확실한 언어 경계에서만 분리 정렬하고, 분류나 정렬이 불확실하면 원래 구간 시간으로 되돌린다. 고유명사·숫자·약어의 정렬 실패를 이유로 텍스트를 삭제하지 않는다. [S3]

원본 시간축을 보존한다. 청크 경계의 중복·누락을 처리하고, 무음 제거를 하는 경우 원본 시각으로 복원할 매핑을 남긴다. 최소한 구간 단위 재생은 항상 가능해야 한다.

### 6.3 pyannote 전체 회의 처리

`community-1`의 regular 결과와 exclusive 결과를 별도로 보존한다. regular는 겹친 발화 정보를, exclusive는 전사 구간과 대표 화자 연결을 위해 사용한다. exclusive가 두 목소리의 말을 분리 복원하는 기능이라고 안내하지 않는다. [S4]

자동 모드는 `min_speakers=1`, `max_speakers=12`, 수동 모드는 실제 발화자 수 `num_speakers`를 사용한다. 참석 인원과 실제 발화자 수의 차이를 UI에 설명한다. 0명·13명 같은 값은 거부한다.

화자 군집은 전체 회의 기준으로 생성한다. ASR을 청크로 나누었다고 청크별 `SPEAKER_00`을 같은 사람으로 간주하지 않는다. 끝부분에 처음 말한 사람이 나타나는 경우도 확인한다.

### 6.4 전사와 화자 연결

Whisper 세그먼트 하나에 여러 화자가 포함될 수 있으므로 **전사 세그먼트 하나당 임베딩 하나를 뽑아 새 화자 여부를 결정하는 방식은 구현하지 않는다.** 정렬된 단어 또는 최소 발언 구간과 음향 화자 구간의 시간 겹침을 바탕으로 연결하고, 필요하면 표시 구간을 화자 전환 지점에서 나눈다.

짧은 맞장구·동률 배정·겹친 발화·정렬 실패는 `needs_review` 또는 화자 미확정으로 남긴다. 임의 수치를 “정확도 95%” 같은 확률로 표시하지 않는다. 배정 이유와 사용한 근거를 보존한다.

### 6.5 임베딩 보정의 구현 범위

pyannote가 계산한 임베딩을 어댑터에서 얻을 수 있는지 고정 버전으로 확인한다. 현재 WhisperX 래퍼와 pyannote 출력은 버전에 따라 차이가 있으므로 공개 인터페이스를 우선 사용한다. 필요한 경우 작은 자체 어댑터를 두되 라이브러리를 광범위하게 포크하지 않는다. [S5]

화자별로 충분하고 겹치지 않는 대표 구간을 여러 개 사용해 군집 대표값을 만들고, 유사한 화자 쌍을 **병합 후보**로 제시한다. 필요한 임베딩을 얻지 못하면 이 기능을 조용히 없애지 말고 호환 어댑터를 수정하거나 명시적으로 차단 사유를 기록한다.

후보 점수는 유사도이지 확률이 아니다. 범용 고정 임계값 하나로 자동 병합하지 않는다. 사용자가 후보를 확인하고 대표 음성을 듣고 병합하거나 무시할 수 있게 한다. 적용 전 결과와 수정 이력을 저장하고 되돌릴 수 있게 한다.

교정 품질은 pyannote 원본 대비 오병합·오분리·미확정 비율로 비교한다. 미확정만 늘려 정확도가 좋아졌다고 주장하지 않는다. **자동 재군집화·자동 병합은 MVP 기본 경로에 넣지 않는다.**

## 7. Codex CLI 회의록 생성

### 7.1 공급자와 인증

실제 구현체는 `CodexCliProvider` 하나뿐이다. 입력/출력 계약과 실행기를 분리하되 쓰지 않을 공급자 프레임워크·Gemini 코드·API 키 설정 화면을 만들지 않는다.

개인 구독 로그인은 별도 런타임 `CODEX_HOME`에서 사용한다. 장비를 바꾸면 소유자가 그 장비에서 로그인한다. 릴리즈에는 인증 파일·브라우저 쿠키·개발 세션 ID가 포함되면 안 된다. 실제 CLI 경로·버전·모델·로그인 방식은 설정·진단에서 확인한다. [S6]

음성·영상과 화자 임베딩은 외부로 보내지 않는다. 전사 텍스트·회의 메타데이터·필요한 근거 ID만 보내며, 로컬 STT가 전체 오프라인 서비스를 의미하지 않는다는 안내를 설치와 생성 화면에 둔다. 외부 텍스트 처리를 허용하지 않은 회의는 전사까지만 처리한다.

### 7.2 실행 격리와 파싱

인자 배열과 표준 입력으로 실행하며 `shell=True`, 사용자 문자열이 섞인 셸 명령, 파일명을 명령으로 해석하는 방식을 금지한다. 회의 원문은 프로세스 명령줄에 넣지 않는다.

사전작업에서 검증한 최소 권한·별도 작업 디렉터리·별도 런타임 홈을 사용한다. 개발용 AGENTS, 플러그인, hooks, MCP, 웹 검색, shell 도구를 상속하지 않는다. 입력은 명령이 아니라 데이터라는 시스템 규칙과 실제 실행 권한 경계를 함께 둔다.

`codex exec`, JSON Schema, 최종 응답 파일 또는 검증된 JSONL 이벤트를 사용한다. 진행 로그를 최종 JSON으로 파싱하지 않는다. stdout/stderr는 크기를 제한하고 전사문·토큰을 기본 로그에서 제거한다. `--ephemeral`을 사용하되 서버 보관 설정과 별개임을 유지한다. [S7]

종료 코드뿐 아니라 스키마·근거·필드 검증이 성공해야 완료다. `command_execution`·MCP 등 예상하지 않은 도구 사용이 관측되면 정상 결과로 받아들이지 말고 격리 설정을 확인한다. 테스트 입력으로 명령 실행·토큰 읽기·외부 전송 유도를 넣어 무해하게 차단을 확인한다.

### 7.3 회의록 스키마

필수 필드는 `schema_version`, `meeting_id`, `transcript_version`, `revision`, `language`, `status`, `summary`, `topics`, `decisions`, `action_items`, `open_questions`, `review_notes`다. 빈 안건·결정·할 일은 빈 배열로 허용한다.

할 일 예시:

```json
{
  "id": "action_01",
  "task": "부하 테스트 결과를 정리한다.",
  "owner_speaker_id": null,
  "due_date": null,
  "due_date_original_expression": "다음 주까지",
  "source_segment_ids": ["seg_104", "seg_105"],
  "review_status": "needs_review"
}
```

담당자·기한이 없으면 null로 둔다. 실제 회의 일시가 없거나 날짜 표현이 모호하면 절대 날짜로 바꾸지 않는다. 실제 회의 날짜와 시간대가 명확할 때만 상대 날짜를 해석하고 원래 표현도 보존한다.

의견·제안·결정·번복을 구분한다. 뒤쪽에서 번복한 앞선 결정을 현재 확정 사항으로 남기지 않는다. 각 결정·할 일은 실제 전사 버전의 근거를 가져야 한다. 사용자 직접 추가 항목은 `사용자 작성`으로 표시하고 가짜 음성 근거를 만들지 않는다.

서버는 ID 존재, 유효한 화자, 시간 범위, 형식, 길이·항목 수 상한을 검사한다. **근거 ID가 존재한다는 사실만으로 의미가 맞는지는 보장되지 않는다.** 의미 검증은 고정 평가 사례·사용자 검토와 함께 다룬다.

### 7.4 긴 전사문과 호출 예산

2시간 입력을 조용히 잘라 요약하지 않는다. 선택한 모델의 실제 입력 한도와 출력·시스템 지시 예산을 기록하고, 입력이 허용 범위이면 전체 문맥으로 처리한다.

입력이 큰 경우에만 근거 ID를 유지한 안건·결정·할 일 후보 추출 → 전체 통합의 두 단계로 처리한다. 단순 짧은 요약문 재요약으로 근거를 잃지 않는다. 청크는 같은 작업 안에서 순차 실행한다.

기본 짧은 회의는 한 번 생성한다. 구조 오류 수정은 한 번만 추가하고, 일시 통신 오류 재시도는 지수 지연·상한을 둔다. 모든 호출을 합한 작업당 기본 상한은 10회로 시작하며 설정으로 조정한다. 무한 JSON 수리·청크 재시도·모델 자동 교체는 금지한다.

동일 전사 버전·모델·프롬프트·설정 지문의 이미 완료된 결과는 재사용한다. 사용자가 새 초안을 명시적으로 요구한 경우에만 새 생성 시도를 만든다.

### 7.5 오류·한도·취소

로그인 필요, 구독 한도, 모델 접근 불가, 네트워크, 시간 초과, 잘못된 JSON, 근거 검증 실패를 구분한다. CLI의 구조화 오류가 있으면 우선 사용하고, stderr 문자열 처리는 버전별 제한된 호환 계층으로 둔다.

구독 잔여량을 공식적으로 얻지 못하면 `확인 불가`라고 표시한다. 이 앱의 토큰 기록을 계정 전체 잔여량으로 표현하지 않는다. 사용량 초기화 시각이 확인되지 않으면 임의로 채우지 않는다.

요약 실패·취소 후에도 전사문은 남는다. 사용자에게 회의록 생성만 다시 요청할 수 있게 한다. 취소가 외부 서비스에서 이미 소비한 사용량을 되돌리지 않는다는 점을 안내한다.

## 8. 웹 UI와 API

### 8.1 화면

**회의 목록**: 제목, 회의 일시, 길이, 진행/오류, 초안/확정, 검색·필터, 업로드 진입.

**업로드·설정**: 파일 선택/드롭, 업로드 바이트 진행, 제목·언어·실제 회의 일시·화자 수·외부 텍스트 처리 허용, 형식 오류 안내.

**대기열**: 실행 중 카드, 단계·경과 시간, 대기 순서, 차단 사유, 취소·재시도·전사만 종료. 약 2초 간격 폴링으로 시작한다. 정확한 진행 비율을 얻지 못한 단계는 진행 중 표시만 사용한다.

**회의 상세**: 음성 플레이어와 화자별 전사문, 한글 회의록. 근거 클릭 이동, 화자 이름/발언 수정·병합 후보·되돌리기, 버전 선택, 초안 수정·확정, 내보내기·삭제를 제공한다.

**설정·진단**: 저장소·보관 기간, CPU 스레드, 모델 상태, 런타임 Codex 경로·로그인 여부·실제 모델, 확인 가능한 앱 사용량. 비밀번호·토큰 원문은 표시하지 않는다.

화면은 한글로 만들고 키보드 조작, 폼 레이블, 오류 텍스트, 삭제·병합 확인을 제공한다. 디자인 시스템이나 협업 편집기를 과도하게 도입하지 않는다. Markdown 렌더링은 HTML 실행을 허용하지 않는다.

```text

POST   /api/v1/meetings/{id}/speakers/merge

PATCH  /api/v1/meetings/{id}/minutes/{revision}
```

실제 구현에서 경로를 조정할 수 있지만 OpenAPI·프런트 클라이언트·테스트를 일치시킨다. 비동기 요청은 202와 작업 ID를 반환한다. 전사 편집은 기대 버전, 작업 등록은 멱등성 키를 받는다. 오디오 재생은 탐색을 위한 Range 요청을 지원한다.

기본 API·웹은 같은 출처에서 제공한다. Vite 개발 서버는 `/api` 프록시로 연결하고 `CORS=*`를 사용하지 않는다. WSL 개발에서는 Windows의 localhost 접근을 실제 확인한다.

## 9. 보안·보관·확장 경계

### 9.1 개인용 접근 제어

기본 바인딩은 `127.0.0.1`이다. 개인 소유자용 로컬 부트스트랩 인증 후 HttpOnly·SameSite 세션 쿠키를 사용하고, 상태 변경 요청의 Origin/CSRF와 Host를 검사한다. 로컬 토큰은 빌드된 JS·Git·로그에 넣지 않는다. 진단 API도 같은 인증을 거친다.

루프백 전용이라도 외부 웹 페이지가 로컬 API를 호출하지 못하도록 한다. 인증 없는 업로드·삭제·파일 읽기·Codex 호출을 허용하지 않는다. LAN 바인딩·공유 링크·공개 배포는 MVP에서 비활성화한다. 다른 PC에서 서버 UI에 접속할 필요가 생기면 별도 범위로 취급하며, 배포 번들 자체는 각 개인 장비에 설치할 수 있게 한다.

### 9.2 파일·프로세스·데이터

미디어·임시 파일·결과 경로를 서버가 통제한다. HTTP 요청에서 임의 로컬 경로나 외부 URL을 받지 않는다. FFmpeg에 실행 시간·출력 크기·자원 상한을 적용하고 디코더의 네트워크 프로토콜을 제한한다.

로그는 작업 ID·단계·성능·오류 코드 중심이다. 원본 전사, 생성 프롬프트, 토큰, 인증 헤더, 화자 임베딩은 기본 로그에서 제외한다. 로그 크기·회전과 임시 디렉터리 청소를 구현한다.

보관 기간은 원본 영상·추출 음성·전사/회의록별로 설정한다. 기본값은 사용자 직접 삭제 전까지 유지하고 자동 삭제는 명시적으로 켠다. 음성이 삭제되면 근거 텍스트는 유지하되 재생 불가를 표시한다. 삭제 API는 진행 작업을 안전하게 중단하고 원본·파생 파일·임베딩·DB 참조를 정리한다.

백업은 일관된 SQLite 백업과 참조 파일 manifest로 구성한다. 로그인 자격 증명은 일반 회의 백업에서 제외한다. 복구가 실제로 동작하는지 작은 자료로 확인한다.

### 9.3 외부 연동은 경계만 준비

회의록 정본은 서비스 독립 JSON이다. Markdown/텍스트 출력은 렌더러로 분리한다. `minutes.generated`와 `minutes.approved` 의미를 도메인 이벤트 계약으로 구분하고 문서에 남긴다.

Slack·Notion·Confluence SDK, OAuth 화면, 토큰 저장, 발행 워커, 실제 Outbox 전달 시스템은 이번에 구현하지 않는다. 나중에 확정된 `(meeting_id, revision)`을 발행 어댑터에 넘기고 중복 방지·외부 문서 ID·수정 충돌·삭제 정책을 추가할 수 있게 핵심 도메인이 외부 서비스에 의존하지 않도록 한다.

## 10. 구현 단계 G1~G6

각 단계는 구현 → 해당 범위의 최소 확인 → 12.1절의 계획 차이 확인·최신화 → 증거·체크포인트 저장 순서로 수행한다. 검증 세션 호출은 정해진 R1/R2/R3에 묶는다. 문서 동기화를 마쳐야 해당 마일스톤의 완료를 기록한다.

### G1. 골격·계약·실행 도구

구현할 것:
- 준비 완료 결과를 읽고 기존 저장소를 조사한다. 없는 코드만 추가한다.
- 백엔드/프런트 구조, 잠금 파일, 설정·로깅·마이그레이션을 만든다.
- 엔터티·작업 상태·회의록 스키마·어댑터 인터페이스를 고정한다.
- 데이터 경로·설정·소유자 인증의 골격과 health/diagnostics를 만든다.
- `.workflow/state.json`의 재개 형식과 빠른 검사 명령을 마련한다.
- 준비용 `scripts/verify_dispatch.py`를 그대로 MVP 요청기로 간주하지 않는다. 3.3절의 `VERIFY_REQUEST`와 고정 UUID·요청 ID·SHA·패킷을 사용하는 구현용 전송 절차를 마련한다. R1/R2는 전체 회귀를 금지하고, R3의 `allow_full_suite=true`는 마스터가 명시한 릴리즈 요청에만 허용한다. 모델·실제 Codex 실행 허용은 별도 패킷과 예산에 따르며 자동으로 확대하지 않는다. 중복 전송 방지와 불명확한 전송 결과의 재개 처리를 유지한다.
- 3.4절의 `VERIFY_RESULT`와 세 판정값을 사용하고, 결과 확인·처리 기록 후 `scripts/consume-review-acks.py`로 해당 알림만 삭제하는 기존 절차를 연결한다. Windows 세션·큐 유지 예외는 `.workflow/preflight.json`의 승인 결정을 따른다.

완료 증거: Ubuntu/WSL에서 API·웹 부팅, SQLite 초기화/마이그레이션, 스키마 직렬화, 루프백·인증 기본 계약 시험. 구현용 검증 전송 절차의 R1/R2 전체 회귀 거부, 명시적 R3 전체 회귀 허용, 중복 방지를 모델 호출 없는 계약 시험으로 확인한다. 기존 유효한 큐 왕복·알림 소비 증거는 재사용하고 전송 경로가 달라진 경우에만 한정 왕복을 확인한다. 모델을 다시 실행할 필요는 없다. **별도 리뷰 없음.**

## 11. 테스트 전략과 실행 비용

### 11.1 검사 계층

| 계층 | 내용 | 실행 시점 |
|---|---|---|
| 빠른 검사 | 타입·lint·스키마·대상 단위 테스트 | 관련 코드 변경 후 |
| 통합 | DB·큐·프로세스·FFmpeg·API | 해당 경계 변경 후 |
| 웹 E2E | 고정 전사/회의록으로 UI 검증 | 사용자 흐름 변경 후 |
| 실제 모델 | CPU ASR·정렬·pyannote | 최초 연결, 모델/입력 처리 변경 |
| 실제 Codex | 실제 인증·한글 구조화 출력 | 최초 연결, 실행/스키마/핵심 프롬프트 변경 |
| 장시간 | 120분 처리·메모리·취소·복구 | 릴리즈 후보에서 필요한 사례만 |
| 전체 회귀 | 빠른+통합+mock E2E 전체 | R3 기본 1회 |

`model`, `slow`, `live_codex` 마커로 비용 큰 시험을 명시적으로 분리한다. 일반 테스트 명령은 다운로드·실제 모델·실제 CLI 호출을 하지 않는다. “skip”과 “PASS”를 구분한다.

### 11.2 구현해야 할 검사 명령 계약

다음 명령 이름은 프로젝트 도구로 구현한다. 현재 설치된 외부 명령이라고 가정하지 않는다.

```bash
./scripts/check.sh fast             # 정적·단위: 모델·외부 호출 없음
./scripts/check.sh affected         # 지정 변경 범위의 테스트만
./scripts/check.sh integration      # 로컬 계약·프로세스 시험
./scripts/check.sh e2e              # 고정 결과 기반 웹 E2E
./scripts/check.sh model            # 명시적 승인/예산 하의 실제 CPU 모델
./scripts/check.sh live-codex       # 공개·가상 텍스트만 실제 구독 호출
./scripts/check.sh soak             # 120분 경계·장시간 검사
./scripts/check.sh release          # 전체 저비용 회귀 + 실제 증거 유효성 검사
```

`release`가 내부적으로 모든 고비용 시험을 다시 실행하지 않게 한다. 실제 증거가 오래됐거나 영향 코드가 바뀌면 필요한 재실행 목록과 이유를 반환한다. 로그에는 fixture hash, 코드·잠금 파일·설정·모델·프롬프트 지문을 남긴다.

### 11.3 품질·성능 측정

한국어·영어 3분 내외 샘플의 전사·화자·회의록을 구분해 평가한다. 검증된 정답이 있으면 한국어 CER, 영어 WER, 화자 DER 및 오병합/오분리/미확정을 기록한다. DER은 collar·overlap 포함 여부·화자 매칭 조건도 기록한다. 정답이 없으면 숫자를 만들지 않는다.

회의록은 결정 사항 누락, 제안을 확정으로 바꿈, 번복 누락, 없는 담당자·기한 생성, 근거 불일치를 평가한다. 사람이 확인했는지, 공인된 라벨인지, 자동 검사만 했는지 구분한다. 검증되지 않은 자막을 정답으로 놓고 정확도를 확정하지 않는다.

성능은 최초 모델 로딩, 캐시된 실행, 각 단계의 wall time, 전체 RTF, 프로세스 트리 최대 RSS, 스왑, 취소 지연을 기록한다. 처리 속도 목표를 임의로 통과 숫자로 만들지 않는다. CPU 모델 선택을 몰래 낮춰 성능 수치를 맞추지 않는다.

3분 테스트만으로 12명·2시간 품질을 보장하지 않는다. 12명 경계는 설정·화자 ID 유지 계약과 가능한 실제 자료로 확인하며, 실제 12인 회의 품질을 측정하지 못하면 그 제한을 릴리즈 고지에 남긴다.

### 11.4 장시간 시험의 최소 범위

- 7,200초 허용과 초과 거부를 작은 계약 시험으로 확인한다.
- 허가된 샘플로 만든 120분 파일 또는 실제 허가 자료로 **실제 로컬 파이프라인 전체**를 최소 한 번 실행해 OOM·시간축·복구 가능성·출력 크기를 검사한다.
- 반복해서 늘린 파일은 장시간 안정성 자료로만 표시한다. 실제 장시간 다인 회의 정확도 자료로 표시하지 않는다.
- 긴 전사문의 Codex 입력 예산·청크·최종 통합은 고정 fixture로 시험하고, 실제 CLI의 길이 처리 증거도 남긴다. 매 반복 음성에서 동일한 긴 요약을 계속 생성할 필요는 없다.
- 취소·복구 결함은 짧고 결정적인 재현 테스트로 먼저 고친다. 수정 하나마다 2시간 전체 실행을 반복하지 않는다.

장시간 실제 시험이 불가능하면 파일 제한은 구현하되 최종 상태를 `PREVIEW / NOT_FULLY_VERIFIED`로 남긴다. 사용자가 요청한 완전 MVP 완료로 표시하지 않는다.

## 12. 지속 상태·진행 보고·차단 처리

마스터는 `.workflow/state.json`을 직접 관리한다. 검증 세션은 자기 리뷰 결과만 쓴다.

```json
{
  "schema_version": 1,
  "phase": "G3",
  "completed_steps": ["G1", "G2"],
  "last_checkpoint_commit": "실제 SHA",
  "in_progress": "현재 한 작업",
  "next_actions": ["다음 실행 가능한 작은 작업"],
  "pending_reviews": ["R1-001"],
  "evidence_index": "실제 경로",
  "blockers": [],
  "decisions": [],
  "status": "IMPLEMENTING"
}
```

상태는 작은 작업 묶음 완료, 리뷰 요청/수신, 설정 변경, 차단, 컨텍스트 정리 직전에 저장한다. 전체 대화·로그를 매번 다시 읽지 말고 상태·관련 명세·변경 파일만 읽는다.

목표와 관련 없는 리팩터링, 모든 파일 재포맷, 대형 라이브러리 교체, 과도한 디자인 수정으로 범위를 넓히지 않는다. 범위 안의 사소한 선택은 마스터가 결정하고 근거를 남긴다.

일시 오류는 제한적으로 재시도한다. 계정·관리자 권한·사용량·법적 이용 허가·지원 불가 환경처럼 스스로 해결할 수 없는 차단은 반복 호출하지 않는다. 독립 구현을 계속하고, 남은 차단과 필요한 조치를 모아 보고한다. 이때 완료 조건을 축소하거나 테스트를 지워 목표를 충족한 것으로 만들지 않는다.

CLI·세션이 중단되면 기존 세션을 재개하고 `preflight.json`, `state.json`, 세션 레지스트리, 미완료 리뷰 순으로 확인한다. 프로세스가 계속 실행 중인지 먼저 확인해 중복 작업을 만들지 않는다. 검증 세션 UUID가 바뀌면 큐 등록·왕복만 갱신한다.

### 12.1 마일스톤 완료 전 계획 최신화

목적은 이 문서를 항상 현재 구현과 다음 작업에 맞는 실행 기준으로 유지하는 것이다. 마스터는 G1~G6 각각의 완료 전에 다음을 수행한다. 다음 단계나 리뷰에 영향을 주는 변경은 확정 즉시 반영한다.

1. 실제 구조·계약·의존성·경로·실행 명령·검증 방식·단계 배치가 문서와 다른지 확인한다. 승인된 범위의 변경은 관련 절을 직접 고치고, 서로 연결된 절과 후속 단계도 함께 맞춘다. 폐기된 지시는 남기지 않는다.
2. 구현 결함이나 미완료 요구를 문서에서 지워 완료로 만들지 않는다. 사용자 목표·필수 완료 조건·승인 경계를 바꾸는 경우에는 기존 사용자 결정을 따르며, 새로운 결정이 필요하면 해당 부분을 미결로 유지한다.
3. 변경이 있으면 문서 버전과 최종 갱신일을 갱신하고 Linux 원본과 Windows 사본을 동기화한다. `.workflow/state.json`의 `plan_sync`에는 해당 마일스톤, `UPDATED`/`NO_CHANGE`/`PENDING`, 문서 버전만 남긴다. 상세 변경 사유·별도 변경 이력 파일은 만들지 않는다. 최신화가 `PENDING`인 마일스톤은 완료 처리하지 않는다.
4. 검증 계약이 달라졌으면 영향받는 검사만 기존 R1/R2/R3 또는 범위 재검증에 연결한다. 문서 정리만으로 추가 전체 검증을 실행하지 않으며, 진행 중인 검증 snapshot은 바꾸지 않는다. R3 요청 전에는 최신 문서도 릴리즈 후보와 함께 고정한다.

## 14. 릴리즈 산출물과 운영 안내 계약

릴리즈 이름의 예시는 `local-meeting-minutes-0.1.0-ubuntu24.04-x86_64.tar.gz`다. 이는 목표 산출물 이름이지 현재 생성됐다는 의미가 아니다. 소스·고정 의존성 정의·빌드된 웹 자산·설치/실행/정지/진단/모델 준비 스크립트·세 문서·이용 고지를 포함한다.

개인 로그인 파일, 로컬 회의, 임베딩, 실제 원문 로그, 검증 세션 ID, `.workflow`의 개인 환경 정보, 라이선스가 허용하지 않는 테스트 미디어는 포함하지 않는다. 모델 파일을 기본 번들에 넣지 않고 소유자가 필요한 모델 사용조건을 확인한 뒤 준비하게 한다. 선택한 모델·라이브러리의 고지·재배포 조건은 릴리즈 단계에서 확인한다.

아래 운영 명령을 구현하고 실제 옵션·설치 경로로 이 절을 갱신한다.

```bash
./scripts/install-ubuntu.sh        # 사용자 영역 설치, 시스템 의존성은 별도 안내
./scripts/login-codex.sh           # 런타임 홈에서 소유자가 로그인
./scripts/prepare-models.sh        # 모델 준비·캐시 검사
./scripts/doctor.sh                # 환경·모델·로그인·로컬 연결 점검
./scripts/run.sh                   # API와 단일 작업 관리자 시작
./scripts/stop.sh                  # 자신의 프로세스만 안전하게 종료
./scripts/backup.sh                # 일관된 DB·자료 백업, 인증 정보 제외
./scripts/restore.sh <backup>      # 새 데이터 경로에 복원, 기존 데이터 보호
```

설치 과정이 관리자 권한을 필요로 하면 정확한 시스템 패키지 설치를 분리하고 이후 앱을 root로 실행하지 않는다. 프로덕션 실행은 정적 프런트를 FastAPI에서 제공해 Node 개발 서버를 상시 띄우지 않는다.

systemd 사용자 서비스는 선택적으로 제공한다. 로그인한 서비스 사용자·HOME·CODEX_HOME·PATH를 명시하고, 종료 시 자식 프로세스 정리를 시험한다. GUI 로그인과 서비스 실행 사용자가 다르면 인증을 공유한다고 가정하지 않는다. WSL에서 서비스 지원이 없는 경우 `run.sh`로 개발하되 Ubuntu 릴리즈의 사용자 서비스 설치 경로는 별도로 검증한다.

Windows에서는 `scripts/dev-windows.ps1`로 올바른 WSL 배포판·Linux 저장소를 실행하고 Windows 브라우저로 localhost를 연다. 경로에 공백·한글이 있어도 인자 처리가 안전해야 한다. Windows 네이티브 Python 런타임 지원이나 `.exe` 패키징을 완료 항목에 추가하지 않는다.

외부 네트워크 공개·GitHub 릴리즈 게시·원격 push는 이 목표에 포함하지 않는다. 로컬 릴리즈 산출물을 만들고 실제 배포 공개는 사용자의 별도 지시를 따른다.
